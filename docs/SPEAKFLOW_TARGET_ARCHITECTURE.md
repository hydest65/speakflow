# SpeakFlow Target Architecture

## 1. Direction

SpeakFlow should borrow the useful architecture pattern from mature video-learning products without copying their visual identity:

- Static/SPA frontend for learning workbench screens.
- Backend API as the only trusted boundary for auth, upload, AI, storage, and admin actions.
- Structured learning data split into videos, subtitles, highlights, cards, and user progress.
- Dual video-source model so each video can later use local object storage, Tencent COS/VOD, R2/S3, or Cloudflare Stream.
- AI as an optional enhancement, not a required dependency for the base subtitle workflow.

The UI style remains undecided. This document only fixes the technical shape.

## 2. Runtime Layers

```text
Browser
  -> SpeakFlow frontend pages
  -> SpeakFlow backend API
  -> PostgreSQL-compatible data model
  -> Object storage / video delivery
  -> Optional workers for FFmpeg, ASR, and MiniMax notes
```

Current MVP keeps the same shape but uses local JSON instead of PostgreSQL:

```text
server.js
  -> data/app-data.json
  -> data/subtitle-jobs.json
  -> processing/
```

## 3. Core Resources

### videos

Primary video metadata and delivery source.

Fields:

- `id`
- `title`
- `description`
- `thumbnail_url`
- `thumbnail_url_cn`
- `cloudflare_stream_id`
- `tencent_cloud_url`
- `source_url`
- `status`
- `difficulty`
- `duration`
- `display_order`
- `created_at`

### subtitles

Timed bilingual subtitles.

Fields:

- `id`
- `video_id`
- `start_time`
- `end_time`
- `english_text`
- `chinese_text`

### subtitle_highlights

Precomputed word and phrase highlights for each subtitle cue.

Fields:

- `id`
- `subtitle_id`
- `highlighted_html`
- `word_matches`
- `phrase_matches`
- `created_at`
- `updated_at`

### learning cards

Close-reading content split by type:

- `word_cards`
- `phrase_cards`
- `expression_cards`

These can be generated manually, imported from spreadsheets, or optionally generated by MiniMax later.

### user progress

User state should stay separate from course content:

- `user_video_progress`
- `user_learning_progress`
- `user_learning_calendar`
- `favorites`
- `collections`

## 4. API Shape

The MVP now exposes these production-shaped routes:

- `GET /api/videos`
- `GET /api/videos/:videoId/detail`
- `GET /api/videos/:videoId/subtitles`
- `GET /api/videos/:videoId/subtitle-highlights`
- `GET /api/learning/videos/:videoId/close-reading`
- `GET /api/user/video-progress/:videoId`
- `POST /api/user/video-progress`

Existing subtitle-lab routes remain:

- `POST /api/subtitle/jobs`
- `GET /api/subtitle/jobs/:jobId`
- `PUT /api/subtitle/jobs/:jobId/cues/:cueId`
- `GET /api/subtitle/jobs/:jobId/export`
- `GET /api/subtitle/diagnostics`

## 5. Cost Control

Base version:

- No large language model required.
- User can paste transcript, import subtitles, edit notes, and export files.
- Real video transcription still needs ASR if no subtitle file/transcript is provided.

MiniMax enhancement:

- Optional note generation.
- Optional word/phrase/expression card generation.
- Optional speaking feedback.

This lets SpeakFlow sell a useful non-AI tool while keeping MiniMax usage metered.

## 6. Security Rules

- Never put service-role database keys in frontend code.
- Never put Cloudflare, S3, R2, Tencent Cloud, or MiniMax secret keys in frontend code.
- Admin writes, upload signing, video deletion, AI calls, and batch generation must go through backend API.
- Frontend route guards are only UX; backend authorization is the source of truth.

## 7. Migration Path

1. Keep local JSON API compatibility while UI and product flow are still moving.
2. Replace `data/app-data.json` with PostgreSQL tables using the same resource names.
3. Move long-running jobs to BullMQ/Celery.
4. Move video files to object storage and use signed upload/download URLs.
5. Add admin screens after the data model is stable.
